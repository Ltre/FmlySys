## 32. 成员软删除、成员资料维护、后台快速记录处理与转账用途展示

日期：2026-08-24

### 32.1 成员删除统一改为零余额软删除

此前 `DeleteMemberSmart` 会根据成员是否被业务/审计记录引用，在“物理删除”和“软删除”之间选择。该规则会让一个没有历史引用的成员行真正消失，与本轮“后台删除成员永远只做标记删除”的要求冲突。

本轮把删除语义固定为：

```text
后台点击标记删除
→ 先进入与资金写入共用的串行 gate
→ 在同一个 SQLite transaction 中计算该成员当前公共资产代管余额
→ 余额 != 0：拒绝删除，成员及认证状态均不改变
→ 余额 == 0：members.is_del=1、status='deleted'
```

余额计算沿用当前完整账本口径，包含：

- 初始资产 / 资产新增 / 资产划出 / 财务调整；
- 成员间转入、转出；
- 使用该成员代管公共资产支付的消费；
- 该成员作为公共资产持有人支付的后续报销。

因此删除检查与系统实际显示的“持有资产”口径一致，并与并发资金写入串行，避免检查为 0 后同时又写入一笔资金变动。

删除成功时只撤销业务访问能力：

- 删除成员登录 session 与权限；
- 解绑微信身份并把原加入申请恢复为可重新申请状态；
- 撤销旧式 Passkey 认证状态；
- 对新的独立 Passkey login identity，删除关联的登录 session / ceremony，并把 `member_id` 解除关联，但保留独立身份及其凭据。

明确不删除、不隐藏：

```text
members 行本身
asset_events
public_expenses
holder_transfers
reimbursements
audit_logs
record_attachments / 历史凭证
```

`MembersForAccounting()` 继续把已删除成员带入历史账务计算，并显示为“姓名（已删除）”。因此成员被停用后，原有资金流水、审计操作记录及其成员姓名仍可追溯，不会因为后台删除动作从账簿中消失。

兼容旧入口的 `DeleteMemberSmart()` 也改为只代理上述软删除，不再存在 hard-delete 分支。

### 32.2 后台成员信息修改

后台“成员与权限”中每个成员增加“修改成员信息 / 标记删除”管理区，可修改：

- 成员姓名；
- 关系 / 备注。

服务端新增独立成员资料更新接口，规则：

- 姓名去除首尾空格后必填，最多 80 个 Unicode 字符；
- 关系 / 备注最多 160 个 Unicode 字符；
- 已标记删除的成员不能再修改资料；
- 修改前后值写入 `audit_logs`，动作类型为 `update/member`。

成员权限保存继续走原接口，成员资料与权限不混在同一写操作里。

### 32.3 后台处理前台快速记录

后台 `/admin` 新增“前台快速记录”区域，管理员能查看所有成员提交的快速记录，包括：

- 原记录人；
- 分类；
- 摘要；
- 提交时间；
- 原附件；
- draft / 已入库状态。

草稿提供“进行数据入库”，进入后台标准化页面。表单字段与前台保持同一套分类逻辑：

- 公共消费；
- 内部转账；
- 登记报销；
- 资产变动登记。

这里必须区分两个身份：

```text
原快速记录提交人 = 资金业务主体
后台 DevActorID   = 正式入库执行人 / 审计 actor
```

例如张三提交一条快速内部转账：后台选择“转给李四”时，正式流水仍是“张三 → 李四”，而不是“后台开发身份 → 李四”。公共消费的经手人、报销付款持有人、资产变动持有人也都继续是原快速记录提交人。

正式入库继续复用第 29 节的原子事务：

```text
创建正式资金记录
+ audit
+ 把 quick_money_note 附件归属迁移到正式记录
+ quick_money_notes 标记 standardized
→ 同一 transaction COMMIT
```

如果原记录成员已经被标记删除，则后台不能再以其名义生成新的资金流水；历史快速记录仍可查看。

## 33. Passkey 可撤销、权限管理迁移、完整编辑与悬浮快捷入口

### 33.1 本轮审计与设计判断

本轮接续上次因网络问题中断的开发，先逐项核对九项需求的路由、Store、模板、权限和测试。记录的是可复核的设计依据与结果：

- Passkey 凭据是登录方式，不是成员业务数据；删除凭据只能影响认证能力，不能删除或软删除已绑定的成员。

- 前台悬浮菜单是权限受控的便捷入口，不代替服务端的权限检查。后台悬浮菜单仍由管理员会话边界保护。
- 微信禁用是临时的全站安全门，应在服务端生效，避免仅靠 JavaScript 被绕过。静态资源与健康检查保持可用，写请求直接拒绝。

### 33.2 Passkey 列表删除

后台 `/admin/passkeys` 的每个凭据新增删除表单和二次确认，路由为 `POST /admin/passkeys/credentials/{id}/delete`。Store 在事务内删除指定凭据：

- 身份仍有其他凭据时，保留 Passkey 登录身份及成员绑定；
- 删除最后一枚凭据时，清理已无法登录的空 Passkey identity，以便该手机号重新注册；
- 无论哪种情况，`members` 行、成员资料、权限及业务流水均不受影响。

同时修复 `AllPasskeyLoginIdentities` 在 SQLite 单连接配置下边遍历外层 rows 边再查询凭据产生的等待：先完成并关闭外层查询，再逐个装载凭据。

## 34. 修复通用编辑表单成功后停留在“提交中”

日期：2026-08-24

### 34.1 现象与影响范围

以下表单的服务端写入已经成功，但浏览器页面没有重新加载，导致按钮仍显示“提交中…”，旧 DOM 也没有显示更新后的数据：

- 前台事务完整编辑：`POST /matters/{id}`；
- 前台信息共享完整编辑：`POST /share/{id}`；
- 后台成员信息保存：`POST /admin/members/{id}/edit`。

### 34.2 根因

三个 handler 在成功后都会回到原页面的指定记录锚点，例如：

```text
/matters#matter-12
/share#archive-8
/admin/authorities#member-3
```

`WithEnhancedFormResponses` 会正确把 303 跳转转换为 JSON 中的 `redirect`。问题在客户端 `app.js`：成功后直接调用 `window.location.assign(target.href)`。当目标与当前页面的 origin、pathname 和 search 都相同，只有 hash 不同时，浏览器仅执行页内锚点跳转，不会再向服务端请求 HTML。因为当前 JavaScript 执行上下文没有被销毁，表单的 busy 状态也一直保留。

### 34.3 修复方案

在通用异步表单逻辑中新增 `navigateAfterSuccess(target)`：

```text
目标 origin/pathname/search 与当前页相同
→ history.replaceState 保留服务端返回的记录锚点
→ location.reload 强制重新请求页面

目标是其他页面或其他查询条件
→ 继续使用 location.assign
```

这个修复放在通用层，因此事务、共享资料和成员信息表单自动获得一致行为。没有把这些表单降级为非异步提交，因而仍保留现有的服务端校验错误就地展示、成功 flash 提示和锚点定位。资金表单继续由 `asset-workflow.js` 的专用提交与新流水定位逻辑处理，不受本轮影响。

### 34.4 验证

实际执行并通过：

```text

Node 行为级模拟：同页锚点执行 replaceState + reload，跨页执行 assign
go test ./...
git diff --check -- web/static/app.js
```

## 35. 按创建人拆分内容权限、重构共享资料页并新增服药管理

日期：2026-08-25

### 35.1 权限拆分与兼容策略

原来的 `matters.manage` 和 `share.manage` 都无法表达“只能管理自己创建的内容”与“可以代管其他成员内容”的差异。本轮替换为四项独立权限：

- `matters.manage_self`：管理自己创建的家族事务；
- `matters.manage_others`：管理其他成员创建的家族事务；
- `share.manage_self`：管理自己共享的资料；
- `share.manage_others`：管理其他成员共享的资料。

创建事务/共享资料要求对应的 `manage_self`；编辑、状态变更和附件管理则读取记录不可变的 `created_by`，由服务端判断当前成员是在管理自己的记录还是他人的记录。页面按钮与服务端复用同一判断函数，避免仅隐藏按钮却仍能直接调用接口。`manage_others` 不自动包含 `manage_self`，使后台可以真正分别分配两种能力；任何管理权限都会自动补齐相应查看权限。

新增 migration `000008_owned_permissions_and_medication.sql`。已有成员若持有旧的宽泛管理权限，升级时会获得对应的 self、others 和 view 三项权限，再删除旧权限行，保持升级前的实际能力不丢失；新授权界面只展示拆分后的权限。

### 35.2 信息共享列表与详情页

`/share` 调整为摘要列表：

- 卡片展示分类、标题、发布日期、发布人、附件数量和正文摘要；
- 摘要先整理连续空白，再用 Go 的 Unicode rune 截取最多 100 个字符，超长内容追加 `...`，不会在 UTF-8 多字节中间切断并产生乱码；
- 列表查询只统计附件数量，不再逐条装载完整附件列表；
- 每张卡片是指向 `/share-info?id=<id>` 的完整链接，列表不再放附件上传控件和“完整编辑资料”入口；
- 桌面端卡片最大宽度 420px，桌面和移动端均保持 16:9，并裁掉预览区域溢出的正文。

新增 `/share-info` 详情页，显示完整正文、全部附件和发布人。具备当前记录管理权限时，页面右上提供“编辑”，附件追加与单附件删除也集中在详情页。更新成功后仍停留在当前详情和锚点，沿用通用异步表单的强制刷新逻辑。

事务列表也增加创建人显示，并按同一创建人权限边界决定是否显示完整编辑入口。

### 35.3 最小化“老大药物服用管理”

该功能涉及健康和隐私，本轮只实现出院后最基本的执行记录，不在系统内提供诊断、剂量建议或自动改药：

1. 依据已经确定的出院医嘱建立每日用药计划，记录成员、药品、每次用量、时间、开始日期和说明；同一药品每日多次服用时按时间分别建计划。
2. 每个计划和日期只有一条服药记录，可登记“已确认服用”或“未服用”、备注、登记人和登记时间；再次登记是有审计记录的更正，不会生成相互冲突的重复行。
3. 页面显示选定日期的计划与结果，以及截至该日期近 7 天的计划次数、已确认服用、未服、未登记和确认服用率。
4. 计划使用结束日期停用，保留既有服药历史，不提供删除历史记录的入口。
